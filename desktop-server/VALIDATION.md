# 电脑串流验证记录

## 0.4.6 缓冲优化 · 2026-10-24

针对投影仪超分卡顿，减少默认 FSRCNNX / 普通转码每段的音频独立解码和 PCM 中间文件，将音画放入同一 FFmpeg 进程。启动时准备约 8 秒视频，向前预取约 16 秒，按实际恢复位置计算缓存余量；快进需要的已有后台任务提升优先级，取消过时预取。新增受 VBV 约束的 VBR 码率档位，缓存版本升至 6。分辨率、帧率、模型、原界面及遥控操作保留。

Android 0.4.6 / code 13 仅对电脑增强模式调整 LoadControl（起播/用户快进约 4 秒、再次缓冲约 8 秒），增加解码器名称、渲染/丢帧计数诊断，修复上一轮发现的播放器退出回调。独立直连保持原缓冲配置。参数含义见 [Media3 官方说明](https://developer.android.com/reference/androidx/media3/exoplayer/DefaultLoadControl.Builder#setBufferDurationsMs(int,int,int,int))。

相同 Android 11 模拟器、相同合成片、独立缓存，分别观察约 60 秒：

| --- | --- | --- |
| 720P → 1080P 起播 | 3.72 秒 | 5.84 秒 |
| 720P → 1080P 冷快进后缓冲采样 | 5/120 | 0/120 |
| 720P → 1080P 播放推进 / 观察时间 | 54.62 / 60.45 秒 | 56.75 / 60.70 秒 |

| 1080P → 4K 最低客户端缓存 | 4.54 秒 | 8.05 秒 |

新版两场景开始采样后的丢帧计数未增长（720P 为 2→2，4K 为 6→6，起播阶段已产生少量丢帧）。但有缓存时仍出现数秒画面/进度不推进，新版 4K 的总播放推进反而少于基线，因此不能将“缓冲采样为零”当作完全流畅或卡顿已根治。当前已改善缓冲余量，仍需投影仪实际片源的解码、时钟与分片衔接诊断。记录 `.desktop-server/sr-performance-before.json`、`.desktop-server/sr-performance-after.json`。

另用相同 1080P 输入、模型、输出尺寸、编码器与 CQ 参数，只对比编码码率控制参数：4 秒 4K 分片从 21,801,608 字节（43.60 Mbps）降至 10,538,904 字节（21.08 Mbps），传输量减少约 51.7%。两者均为 3840×2160 H.264/AAC；更强约束可能增加复杂画面的压缩损失。短分片平均码率可以因 VBV 缓冲而略超 20 Mbps 参数，不能视为严格网络限速。记录 `.desktop-server/sr-bitrate-ab.json`。

验证：电脑服务 23 项测试、13 项真实 GPU 检查、完整模拟器 24 项检查通过；GPU 检查新增独立 880Hz 音轨与原视频 440Hz 音轨的区分，验证单进程选择正确音轨、广告时间轴和 8 秒准备量。Android 18 项单元测试、lintDebug、assembleDebug 通过。完整矩阵仍覆盖各档分辨率、宽屏、29.97 FPS、无音轨、广告、开关、缓存、恢复进度、直连和任务清理，报告 `.desktop-server/sr-046-regression.json`。缓冲策略使首次/换集等待有所增加，缓存重播约 1.2 秒。

### 持续播放阶段拆分与局域网测速 · 2026-10-25（优化前）

用户反馈“画面间歇性卡顿、声音和画面有些不同步”。随后只读观察用户正在播放的 4K 任务，没有重启服务、暂停、换源或修改设置。最初读到一次已失败的旧播放器状态，用户随后的正常新任务为 3840×2160 / 29.97 FPS；本段结论取正常任务。观察期间服务只有 1 个活跃串流任务。

利用工作目录创建时间、输入清单写入时间、编码文件写入及任务目录清理时间，约每 200ms 观察一次，完成 23 段的拆分：每段约 4.004 秒视频，输入准备平均约 1.07 秒，FFmpeg 超分/编码加 FFprobe 校验平均约 4.03 秒，串行合计约 5.10 秒。约 119.19 秒设备状态观察中进度只推进 95.36 秒，120 个约一秒采样中 22 个处于缓冲，丢帧仍为 0→0。

以上是文件系统时间戳估计：输入准备不含工作目录创建之前的缓存预算检查；编码/校验终点最多含约 200ms 观察延迟，不能当作精确 GPU 核函数计时。输入准备同时含片源下载和本地缓存/清单操作，耗时较长的段约 2–3 秒，部分缓存命中段约 0 秒；编码/校验多数约 3.6–4.3 秒。现有 `localWindow()` 在单一工作队列内等待下载，然后才执行编码，未来分片的网络等待没有与当前编码有效重叠。因此当前不能简单断言只有外网慢或只有超分算力不够：4K 处理本身已接近实时上限，串行取流等待又进一步降低持续供给。优先方向是下载预取与编码重叠、减少每个短分片重启工具的固定成本，再验证音画连续性；尚未实施这些后续优化。

阶段观察结束后，用电脑临时 TCP 服务向投影仪发送固定长度数据，设备 `nc | head -c 33554432 | wc -c` 确认每次完整收到 32 MiB，三次约 127.54、129.37、87.42 Mbps。耗时包含 ADB 启动，测试期间仍有播放，属于此时环境的吞吐样本；不保证全片无 Wi-Fi 瞬时抖动。相对于当前 4K 分片约 20 Mbps 的量级，局域网持续带宽不是主要瓶颈的证据较强。测速与阶段观察时间分开，避免把测速竞争计入前面的分段耗时；临时 TCP 服务已关闭。

匹配当前任务编码文件的大小和 inode 创建时间，核查相邻 357–361 号分片：每段视频起点 0.021333 秒、时长 4.004 秒，AAC 起点 0 秒、时长 4.032 秒，均有 120 个视频包与 189 个音频包。约 21ms 的分片起点差不能直接解释或排除用户感受到的不同步；尚未测量实际投射/扬声器延迟，也未确认缓冲恢复及 discontinuity 衔接是否产生额外偏移，不能将音画同步问题标为通过。

报告 `.desktop-server/projector-live-stages.json`、`.desktop-server/projector-live-stages-summary.json`、`.desktop-server/projector-lan-throughput.json`、`.desktop-server/projector-live-av-packets.json`。本段仅诊断并补充记录，未修改处理算法、APK、用户数据或播放状态；读取完成后移除临时 9223 调试转发。

### 下载与编码并行优化 · 2026-10-25

电脑侧改为独立的源片段准备队列与 GPU 编码队列，同一时刻仍最多一个编码任务。下一段的取流/清单准备可以与当前段编码重叠；启动预缓冲同样流水化。已排队的前台请求可提升两个队列的优先级；快进或关闭任务的取消信号传入 HTTP 请求和流写入，包含尚未收到响应头的等待。补上缓存异步检查期间关闭会话后仍可能启动预取的竞争检查。

默认分段从约 4 秒增至约 8 秒，预取 4 段（约 32 秒），启动目标仍为约 8 秒；任意恢复位置向分段边界取整，实际准备量可能更多。8 秒分段减少 FFmpeg / GPU 初始化和 FFprobe 校验次数，但未缓存位置的冷快进可能需要更久。可用 `--chunk-seconds 4` 保留短分段。超分模型、升一档/4K 策略、帧率、编码质量及有界码率参数、遥控界面均保留，APK 无需重装。

新增阶段统计 `sourcePreparationSeconds`、`encodeSeconds`、`validationSeconds`；`processingSeconds` 改为任务准备至编码结束的活跃墙钟时间并集，排除完全空闲等待，不把重叠阶段重复累加。状态 `speed` 按完成的视频时长除以该并集计算。服务能力中返回 `chunkSeconds`、`downloadPipeline`。上述统计与旧版串行累计定义不同，不能只比较该字段就宣称相同比例的加速。

受控真实 GPU 对照使用同一 24.024 秒的 1080P / 29.97 FPS 合成 HLS、FSRCNNX、4K 输出、相同 NVENC 质量与码率参数，给每个未缓存源分片人为增加 1 秒响应等待。串行控制组只是将两个阶段放入同一队列，其他处理逻辑一致，不是重跑旧 APK 或真实外网。每组使用独立缓存，只有一个 GPU 编码任务；首尾分片均核对 H.264/AAC、3840×2160 及音画起点差小于 50ms。

| 配置 | 完整生成耗时 | 预缓冲就绪 | 全链路 / 活跃处理倍速 | 编码时完成的源分片下载 |
| --- | --- | --- | --- | --- |
| serial-4s | 28.69 秒 | 10.50 秒 | 0.84× / 0.90× | 0 |
| overlap-4s | 25.62 秒 | 9.41 秒 | 0.94× / 1.02× | 3 |
| overlap-8s | 21.58 秒 | 8.60 秒 | 1.11× / 1.23× | 1 |

此输入总生成耗时减少约 24.8%，说明下载重叠与减少工具启动有效，但不是投影仪实际片源的固定收益。复现 `node desktop-server/check-pipeline.mjs`，报告 `.desktop-server/pipeline-gpu-validation.json`。

验证：电脑服务 27 项测试通过，含严格串行 GPU、下载编码重叠、快进取消在途取流、关闭资源清理，以及真实 HTTP 响应头等待中的取消。真实 GPU 14 项检查通过，新增 8 秒分段的广告时间轴、独立音轨、音画起点与缓存复用。默认 8 秒流水线的模拟器完整 24 项回归通过，覆盖各分辨率/宽屏/29.97 FPS/无音轨/去广告/遥控快进/播放中开关/重启持久化/缓存/直连/退出清理；20 秒冷快进后观察推进 19.88 秒，无再次缓冲，丢帧不增长。
