# 电脑增强串流 · APK 0.4.2

APK 0.4.2 在原来的「片源管理」面板增加两种播放模式，首页、选片和遥控器逻辑保持原样。默认仍是独立直连。

| 模式 | 视频路径 | 电脑关闭后 |
| --- | --- | --- |
| 独立直连 | 片源 → 设备 Media3 解码显示 | 继续使用 |
| 电脑串流 | 片源 → 电脑过滤广告分片、超分、编码 → 设备 Media3 解码显示 | 提示重试或切回独立直连 |

默认链路：电脑下载网络片源 → 删除明确标记的广告分片 → FSRCNNX 神经网络超分 → H.264/AAC 编码 → 按需 HLS 缓存串流。APP 仍负责搜索、选片、换源和遥控操作，电脑接手播放处理。处理失败会显示错误和重试/直连选项，不会暗中播放未处理的视频。

广告过滤只识别 HLS CUE-OUT/CUE-IN 和明确的广告路径，不凭片段长度猜测；画面内嵌广告、台标和水印不在本阶段能力范围。增强模式禁用设备端二次广告过滤，遵循 APP 的广告过滤开关；切换开关重新建立处理任务。

## 启动服务

Node.js 22.16+，当前默认环境为 Ubuntu 24 x64、支持 Vulkan 的 NVIDIA GPU、FFmpeg 6+（含 libplacebo 和 h264_nvenc）。本机已验证 RTX 3060 Laptop。无新增 npm 依赖，不需要启动旧 Next.js 服务。服务单独使用 8090。

```bash
# 下载校验模型；必要时将 Ubuntu FFmpeg 解包到项目目录，不修改系统软件
npm run desktop:setup

# 只允许本机与 Android 模拟器访问
npm run desktop:server

# 实机连接时，显式监听局域网
npm run desktop:server -- --host 0.0.0.0
```

服务首次启动生成 `.desktop-server/config.json`（文件权限 0600，已加入 Git 忽略）。其中 `token` 是电脑服务配对码。在设备「片源管理」中填写电脑地址和配对码，选择「保存并测试」/「测试连接」，再选择「电脑串流」。模拟器电脑地址为 `http://10.0.2.2:8090`；实机应填写电脑的局域网 IP。配对码仅用于电脑连接，**独立模式无需配对、无需 APP 密码，也没有恢复登录验证**。不要把配对码加到媒体 URL 或公开分享。

本机代理如把公网域名解析到 `198.18.0.0/15`（Fake-IP），可加 `--allow-fake-ip`；此选项只放行域名解析出的该代理地址段，不放行 IP 字面量或普通私网地址。本机实测 DNS 使用此模式，因此联网片源测试开启了该参数。

普通服务默认只读取公网 HTTP/HTTPS 片源。HTTPS 上游由电脑访问，电脑至设备可在可信局域网使用 HTTP；跨不可信网络请使用带 TLS 的入口。服务不提供外网发现或自动开端口功能。

连接检测会报告实际启用的模型和处理能力。首次播放先显示电脑读取、下载和处理进度，首段生成后播放；GPU 串行处理，默认预取后续两段。快进到未处理位置会按需生成，不必等待整片完成。

换集、换源、退出播放会取消子进程并释放前一个任务；服务还会在 30 分钟没有媒体请求后清理任务，最多 8 个并发任务。电脑中断时不会悄悄改成直连，设备提供「重试电脑串流」与「切回独立直连」，保留当前影片与播放位置。服务重启会清空播放任务，需重试创建。

## 模拟器固定测试源

测试源与电脑串流服务是两个独立进程：8091 模拟网络片源，8090 模拟电脑中转。因此停掉 8090 后，设备仍可直接访问测试源。测试视频由 FFmpeg 生成，不下载或存储第三方影片。

```bash
# 生成测试片与默认增强串流均需要 FFmpeg
node desktop-server/generate-fixture.mjs
node desktop-server/fixture.mjs --dir .desktop-server/test-media
```

在另一个终端启动串流服务，仅放行这一个测试 origin：

```bash
npm run desktop:server -- --allow-test-origin http://127.0.0.1:8091
./android-tv/.android-sdk/platform-tools/adb -s emulator-5554 reverse tcp:8091 tcp:8091
```

模拟器「片源管理」添加 `http://127.0.0.1:8091/api`，可暂时只启用这个测试源。搜索 `TV`，播放「电脑串流测试 TV」。第一集是 HLS，第二集是 MP4；都是三分钟 1280×720 合成画面和测试音。串流地址仍填 `http://10.0.2.2:8090`。结束后恢复测试前的播放模式和全部来源勾选；普通外网直连不需要任何 ADB reverse。

测试前备份设备的完整片源勾选，结束时恢复并用普通片名复查，不能把“仅启用测试源”的配置留作日常使用。两种播放模式共用片源勾选；搜索和详情由设备完成，只有开始播放后才连接电脑。电脑服务没有配置或离线，也不应阻止搜索。

验证内容：搜索选片、画面实际渲染、服务流量增加、HLS/MP4 换集、暂停/快进/倍速/画面比例、换集后单一任务、服务中断后提示及直连恢复。可在播放时运行现有遥控器回归：

```bash
node android-tv/scripts/check-native-playback.mjs --report /tmp/libretv-desktop-controls-report.json
npm run desktop:test
npm test
```

服务端测试还覆盖代理 Fake-IP 的显式放行边界、任务超时清理和 DNS 固定地址；并覆盖配对、主/子列表与音轨/密钥/初始化片段重写、上游凭证隔离、Range/HEAD、任务删除、私网限制。真实设备和当前网络片源仍需在模拟器测试通过后另行验证；本阶段不更新投影仪。

## 协议和限制

- `GET /v1/status`：协议版本、实际处理能力、任务数与流量计数。
- `POST /v1/sessions`：原播放 URL、原片进度、广告开关 → 异步 `enhance` 任务和不透明媒体路径。
- `GET /v1/sessions/:id`：处理阶段、错误、输入/输出尺寸、处理倍速、缓存命中与删除广告时间轴。
- `GET/HEAD /v1/sessions/:id/processed/index.m3u8` / `:n.ts`：完整去广告 VOD 时间轴与按需编码分段，支持 Range。
- `GET/HEAD /v1/sessions/:id/media/:asset`：HLS 递归重写，分片/密钥/初始化资源和 MP4 转发；保留 Range 与 206。
- `DELETE /v1/sessions/:id`：取消媒体请求并清理任务。
- 所有请求要求 `Authorization: Bearer <配对码>`。设备凭证不传给上游片源，媒体 URL 不含配对码。
- 公网目标在每次请求及重定向时检查 DNS，并固定已校验的地址。仅测试参数允许精确指定的本地测试 origin。
- 暂不支持 DRM、HDR、直播、HLS 变量/内容转向、DASH、多用户权限。未知处理协议直接报错。

## 播放标注与 4K 档位

0.4.1 在原来的播放标题下增加两行信息，随控制栏显示和隐藏，不改变遥控逻辑：

- `原始 1280×720 → 当前 1920×1080 · 已超分（FSRCNNX）`
- `原始 1920×1080 → 当前 1920×1080 · 未超分（仅转码）`
- 去广告单独显示实际删除的分片数量和秒数；未命中、关闭、MP4 不支持分片过滤分别说明。不能将开关开启等同于已去广告；内嵌广告和水印仍不处理。

0.4.2 默认按片源原始尺寸只提高一个档位：360P → 480P → 720P → 1080P → 4K，已为 4K 的不再放大。540P/576P 等介于档位之间的源升至相邻更高档；裁边宽屏按 16:9 包围尺寸归档，例如 1920×800 → 3840×1600、1280×544 → 1920×816，保持比例。当前播放输出的超分尺寸不参与换源排序，始终比较原始片源分辨率。

不需要为 1080P → 4K 手工切换服务，直接启动即可。显式指定 `--target-height` 时仍可覆盖为固定输出上限，配对和 APP 地址不变：

```bash
npm run desktop:server -- --target-height 2160 --allow-fake-ip
# 手工固定1080P上限（覆盖默认升一档策略）
npm run desktop:server -- --target-height 1080 --allow-fake-ip
# 在另一个端口试验固定4K，APP 需临时改为 :8092
npm run desktop:server -- --port 8092 --target-height 2160 --allow-fake-ip
npm run desktop:check:4k
```

4K 输出最大 3840×2160，宽屏电影保持比例（例如 1920×800 → 3840×1600）。优先选择不超过目标尺寸的原生最高档片源，已达到目标时只转码。FSRCNNX 是 2 倍网络，720P → 4K 使用级联超分，避免把一次网络结果直接拉伸到 3 倍。

本机 RTX 3060 Laptop 对 4 秒 / 24 FPS 合成片实测：1080P → 4K 约 1.15 倍处理速度，720P → 4K 约 0.93 倍；首段准备分别约 3.65 和 4.52 秒。网络、帧率和输入内容会影响速度，多设备/高倍速可能持续缓冲；生成 4K 输出也不代表恢复了原生 4K 的全部细节。投影仪端解码和家庭网络仍需实机验证。

换源列表在默认和原生界面都按原始分辨率降序排列：已知画质高的优先，同分辨率比较响应速度，未知画质及不可用源靠后。当前源保留标记但不强制置顶。探测结果更新会重新排序，并保持焦点和详情仍对应原来的来源；排序和方向浏览不会自动切换播放。

## 模型、缓存与限制

默认 `fsrcnnx` 为 FSRCNNX_x2_8-0-4-1 模型，通过 libplacebo/Vulkan 执行，默认升高一个档位、最高升至 4K，保持比例。低分辨率源使用神经网络放大；源达到目标尺寸则只转码，不宣称超分。超分不能恢复原片已丢失的真实细节。当前默认按约 8 秒切片，音频编码为 AAC，输出为 H.264 SDR。

```bash
# 可选高质量模型（明显更慢，可能持续缓冲）
npm run desktop:setup -- --quality
npm run desktop:server -- --model realesr-general-x4v3

# 显式保留第一阶段原画转发，无 GPU/FFmpeg 依赖
npm run desktop:server -- --processing relay

# NVIDIA 编码不可用时可指定软件编码；超分仍需 Vulkan GPU
npm run desktop:server -- --encoder libx264
```

原片分片和编码产物缓存在忽略目录 `.desktop-server/cache`，默认上限 8 GiB，可用 `--cache-gb 16` 调整。退出后缓存保留供重播复用，按最近访问回收；使用中的文件暂不回收，空间不足明确报错。高质量模式逐帧处理中间文件另占临时磁盘，任务结束或取消后删除。首次处理较慢，再次播放可命中缓存；不会无限占用 GPU 或下载整部 HLS。MP4 当前需先完整下载，单文件受缓存一半和 4 GiB 上限约束，起播可能较慢。

去广告后进度与历史会映射回原片时间，切回直连和继续观看保持原片位置。单个视频限制 8 小时；GPU 串行队列有容量上限。高倍速播放或同时使用多个设备可能超过处理能力而缓冲。独立音轨仅在过滤后时长与视频匹配时支持。编码产物在发布前校验尺寸、音轨、时长及音画起点。

本机连续视频滤镜测试 FSRCNNX 达到约 72 FPS，但完整链路还包含网络、解码、启动和音频处理，不能用该数字保证持续播放。本机模拟器 720P 合成片的完整处理实测约 1.44 倍速（48 秒视频耗时约 33.4 秒），仅代表该测试输入。Real-ESRGAN general 模型本机约 2.3 FPS，适合比较效果或预处理，暂不适合作为默认实时模式。

```bash
npm run desktop:test  # 解析、队列、缓存、HTTP 与安全边界
npm run desktop:check # 真实 GPU：10 秒测试片去除 2 秒广告，编码、音画、快进与缓存
```

### App 超分开关（0.4.3）

片源管理和电脑串流播放设置中的“AI 超分”独立控制每个处理会话。`POST /v1/sessions` 可传 `superResolution: false`，保持原始尺寸并跳过 AI 网络，`adFilter` 仍单独生效；省略或 true 沿用默认升一档/命令行指定档位。输出缓存按开关隔离。更新电脑端代码后需重启现有服务。

### 缓冲与码率（0.4.6）

默认先准备约 8 秒视频，再向前预取约 32 秒（4 段）。下载准备与 GPU 编码使用独立队列，让下一段取流与当前编码重叠；默认 8 秒分段减少工具重启次数，可用 `--chunk-seconds 4` 对照原短分段。较长分段可能增加未缓存位置的冷快进等待。快进需要的分片即使已在后台队列中，也会提升为前台优先级；过时的后台预取会取消。FSRCNNX 与普通转码在同一 FFmpeg 进程处理音画，减少每段的工具启动及 PCM 中间文件。默认分辨率策略仍为升一档，不会因处理慢而自动降低分辨率。

24/30 FPS 的目标/峰值视频码率：720P 为 3/5 Mbps，1080P 为 5/8 Mbps，4K（含电影宽屏）为 12/20 Mbps；高帧率最多放大 1.5 倍，音频另为 AAC 128 Kbps。使用 VBV 约束，短分片平均码率可能暂时超过峰值参数，不能将其视为网络带宽的严格上限。更复杂的画面可能有更多压缩损失。

```bash
# 默认8秒；网络波动时可提高，代价是首次/换集等待更久（允许0–30秒）
npm run desktop:server -- --host 0.0.0.0 --startup-buffer-seconds 12
```

App 0.4.6 电脑增强模式起播/快进恢复需约 4 秒缓存，耗尽缓存后再次播放需约 8 秒；解码侧缓存使用时间与内存约束。这些设置依据 [Media3 缓冲参数](https://developer.android.com/reference/androidx/media3/exoplayer/DefaultLoadControl.Builder#setBufferDurationsMs(int,int,int,int))，不保证处理长期慢于播放时仍能持续观看。`/v1/status` 返回分段长度、下载并行策略、启动预缓冲、预取数量及码率策略；播放任务状态增加 `sourcePreparationSeconds`、`encodeSeconds`、`validationSeconds`。`processingSeconds` 为重叠阶段占用的墙钟时间并集，`speed` 按这个时间计算，不能把各阶段累加后当作串行耗时；需要重启电脑服务使新代码生效。新编码参数使用独立缓存版本，旧文件仍可按 LRU 回收。


同片源 GPU 流水线对照（含人为注入的每源分片 1 秒下载等待，不等同于外网实测）：

```bash
node desktop-server/check-pipeline.mjs
```

对比相同 1080P / 29.97 FPS 输入、FSRCNNX、4K 输出和编码参数的串行 4 秒、并行 4 秒、并行 8 秒三种配置，检查真实视频/音轨与下载编码重叠，报告保存至 `.desktop-server/pipeline-gpu-validation.json`。此对照使用内部 `overlapDownloads: false` 创建串行控制组，不会切换或重启现有 8090 服务。运行时应避免其他超分任务争用 GPU。
